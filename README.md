# local-ai-shell

[![CI](https://github.com/Laith-18/local-ai-shell/actions/workflows/ci.yml/badge.svg?branch=fedora)](https://github.com/Laith-18/local-ai-shell/actions/workflows/ci.yml)

A private, offline AI assistant for the Linux terminal.

Ask it things in plain English. General questions get a straight answer. Questions about the machine get a shell command: read-only commands run straight away and the result is explained in plain English, while anything that changes the system explains *why* it needs permission and waits for you.

```
ai› how much storage do i have

  $ df -h   read-only, running it

  ✦ You have 60 GB free on your system drive and 346 GB free on your game drive.
    (1.4s · 65 tok/s)
```

**Why:** I wanted to see how far a small local model could go as a genuinely useful sysadmin helper, on hardware I already owned, with a £0 budget, no cloud API and nothing leaving the machine. Along the way I benchmarked two very different model architectures on the same box, and the results were more interesting than I expected (see [Findings](#findings)).

> Built with AI assistance (Claude). The hardware setup, benchmarking runs, testing, bug-finding and design decisions are my own.

---

## Features

- **Answers, not just commands.** It decides whether a request needs the computer or is a general question, then either answers directly or runs a command and summarises the output in plain English.
- **Three-tier safety model**
  - *Read-only commands run instantly* (`df`, `ps`, `journalctl`, `systemctl status`, `find` without `-delete`, …), checked against an allowlist per pipeline segment. Redirection, command substitution and write flags are rejected.
  - *Anything that changes the system asks first*, with a plain-English explanation generated by the model and rule-based reasons underneath. High-risk actions (deleting files, `dnf remove`, `curl | sh`, reboots) require typing `yes` in full.
  - *Destructive commands are always blocked* (`rm -rf /`, `mkfs`, `dd` to a disk, fork bombs).
- **Learns from you.** Say "remember that…", "from now on…" or "when I say…" and it stores the rule and follows it in every future request. If you correct a command with `e` and it succeeds, it offers to remember the fix. Manage it with `/learned` and `/unlearn`.
- **Follow-up questions** ("now sort that by size") via short conversation memory.
- **Distro-aware.** The system prompt teaches it Fedora's conventions: `dnf` for packages (with read-only `dnf`/`rpm` queries allowlisted), Flathub for GUI apps, `systemctl --user` for Sunshine, and never touching the NVIDIA akmod. It started life on Bazzite (immutable Fedora Atomic) and was ported to regular Fedora by rewriting the prompts and safety rules; the original Bazzite rules are in the git history.
- **VRAM dynamic.** The model only sits in VRAM while you're using it and is unloaded on exit
- **Guards against small-model failure modes:** token cap and runaway detection, no keyboard input for auto-run commands, and a rule against guessing facts about the machine.
- Streaming replies, a welcome screen with live system stats, and speed and load time shown under every answer.
- Single Python file, standard library only.
- **Tested and evaluated.** ~280 pytest cases (safety classifier, parsing, Ctrl+C handling, eval harness) run in CI on Python 3.11–3.14, plus an automated eval harness for comparing models and prompts on 78 tasks. See [Testing & evaluation](#testing--evaluation).

## How it works

```
ai › "is sunshine running"
        │
        ├─▶ system prompt (Fedora rules + things you've taught it) + recent conversation
        ▼
  Ollama (localhost:11434) ──▶ qwen3.5:4b on the RTX 2060
        │  "$ systemctl --user status sunshine"
        ▼
  safety check ── blocked ──▶ refuse
        │
        ├── read-only ──▶ run immediately, capture output
        └── changes something ──▶ explain + ask ──▶ run in a real terminal (script(1))
        │
        ▼
  output ──▶ model ──▶ "Yes, Sunshine is running and has been up for 2 hours."
```

## Findings

All numbers come from `bench/ai-bench.sh` (raw data in `bench/results/2026-10-01/`): temperature 0, 4K context, thinking disabled unless stated.

### Speed: MoE vs dense on limited hardware

| | lfm2.5 (8B MoE, ~1B active) | qwen3.5:4b (dense) |
|---|---|---|
| Size loaded | 5.4 GB (24% CPU / 76% GPU) | 3.1 GB (100% GPU) |
| Cold start | 22.0 s | 14.1 s |
| Generation, default placement | ~74 tok/s | ~65 tok/s |
| Generation, CPU only | ~24.5 tok/s | ~9.0 tok/s |
| **Speed kept on CPU** | **33%** | **14%** |

The MoE model is twice the size but **2.7× faster on CPU**, because each token only reads the ~1B active parameters rather than the whole model. Even with a quarter of it spilled into system RAM, it outran the dense model that fit entirely in VRAM. The load logs show why: llama.cpp keeps the dense and attention layers on the GPU and pushes the expert weights to RAM, where only a few are touched per token.

Its GPU speed also depends on what else is using VRAM: in an earlier run with ~0.5 GB more free VRAM, only 17% landed on the CPU and it reached 87–94 tok/s.

### Inferring the memory configuration from inference speed

CPU-only, the dense model generated ~9 tok/s while reading ~2.5 GB of weights per token, which works out to roughly **22.5 GB/s** of memory bandwidth. That's above the theoretical maximum of single-channel DDR4-2400 (19.2 GB/s), so the RAM must be running in **dual channel**, and CPU inference here is memory-bandwidth bound.

### Accuracy: the system prompt matters more than the model

Nine command-generation tasks, graded by hand (full answers in `summary.md`):

| | No system prompt | With Bazzite system prompt |
|---|---|---|
| lfm2.5 | 5/9 | 6/9 |
| qwen3.5:4b | **2/9** | **7/9** |

### Thinking can't always be turned off

- **lfm2.5 ignored `think: false` on 100% of requests**, producing identical output with thinking on or off. One-line answers took 1.6–20 s, and one task burned 1,535 tokens of reasoning to produce a nonsense `rpm` command.
- **qwen3.5:4b respects it:** 4–22 tokens and 0.1–0.4 s per answer with thinking off, versus 447 tokens and 6.9 s for the same `df -h` with it on.

**Verdict:** qwen3.5:4b + system prompt is the daily driver. lfm2.5 is the more interesting model to analyse but the worse one to use for this job.

## Failure modes I hit (and fixed)

| Problem | Cause | Fix |
|---|---|---|
| Asked to "install discord", produced a Chromium install followed by hundreds of invented `--no-remote-…-sync` flags (3,849 tokens, 57 s) | Degenerate repetition loop under greedy decoding | Token cap, mild repeat penalty, runaway detection that refuses to offer the command |
| Answered "what's the time" with a made-up time | Model answered from imagination instead of checking | Prompt rule: never guess machine facts or the time; run a command |
| Claimed its speed "depends on your internet connection" | No self-knowledge | System prompt describes what it is and where it runs |
| Wrote an empty file, then said it succeeded | My parser kept only the first line of multi-line (heredoc) commands; the summariser only saw exit code 0 | Heredoc-aware parsing; summary prompt forbids claiming success the output doesn't show |
| After `ujust update` failed, suggested `dnf upgrade` | Summary step didn't get the Bazzite rules | Every prompt in the pipeline gets the same ground rules |
| `ujust update` showed nothing for 90 s | Piped output makes programs buffer and hides prompts | Approved commands run in a real terminal via `script(1)` |
| A `$(cat)` command hung forever | `cat` waiting on keyboard input | Auto-run commands get no stdin; prompt rule against interactive commands |
| Over-explained `echo hello` | Every result was summarised | Trivial or empty output is shown directly ("✓ Done.") |
| Ctrl+C during a command crashed the whole session with a traceback | `KeyboardInterrupt` landed inside `proc.wait()` | Like a real shell, ai-shell ignores SIGINT while a command runs and lets the command handle it; regression test sends SIGINT to the process group |
| `env rm -rf ~/Documents` would have **run without asking** (plus ~15 similar cases) | The read-only allowlist trusted program names, but `env`, GNU `sed`, `uniq`, `rg`, `nvidia-smi` and others can write, delete or execute with the right arguments | Per-program argument checks, found by writing a table-driven test suite (see below) |

## Testing & evaluation

### Tests

```bash
pip install pytest && pytest
```

- **Safety classifier**: table-driven tests for every tier: commands that must be blocked, must auto-run, or must ask (and whether `yes` must be typed in full). A meta-test fails if any `BLOCKED` or `PERMISSION_RULES` pattern has no test case.
- **Read-only bypasses**: writing these tests turned up commands the allowlist treated as read-only, which would have run with no prompt, even though they can change the system. Each now has a named regression test:

  | Looked read-only | What it actually does |
  |---|---|
  | `env rm -rf ~/Documents` | `env` runs whatever command follows it |
  | `sed '1e touch x'`, `sed 's/a/b/e'` | GNU sed's `e` executes shell commands |
  | `sed -n 'w ~/.bashrc'` | `w` writes a file |
  | `sudo nvidia-smi -pl 100`, `--gpu-reset` | changes GPU power limit / resets the GPU |
  | `uniq in.txt ~/.bashrc` | the second argument is an output file, overwritten |
  | `rg --pre CMD`, `awk -i inplace`, `git log --output=F`, `tree -o F`, `ss -K` | run a program, edit in place, write files, kill sockets |
  | `sort -oFILE`, `sort -nro FILE`, `ls >/dev/nullx` | attached or bundled options, and a lookalike of `/dev/null` |

- **Ctrl+C**: runs a command in a child process group and sends SIGINT the way the terminal does; checks ai-shell survives and reports exit code 130.
- **Known limitation, recorded as an `xfail` test**: pipeline splitting isn't quote-aware, so `sed 's|a|b|'` asks permission when it doesn't need to. That's the safe direction to fail in.

### Eval harness

`eval/run_eval.py` replaces the original hand-graded 9-task benchmark. It sends each task through **ai-shell's real pipeline** (same system prompt, same `decide` / `clean_command` / `assess` code) and grades the result automatically. It never runs the commands.

```bash
python3 eval/run_eval.py                                  # default model, 3 repeats
python3 eval/run_eval.py --models qwen3.5:4b lfm2.5       # compare models
python3 eval/run_eval.py --prompt minimal                 # ablation: without ai-shell's rules
python3 eval/run_eval.py --temperature 0.7 --repeats 5    # how stable is it?
python3 eval/run_eval.py --regrade eval/results/<run>      # re-score a saved run after grader/safety changes, no GPU
```

- **78 tasks in `eval/tasks.toml`** across 13 categories: disk, processes, logs, services, packages, files, network, hardware, facts it must not guess (time, hostname), writing files, follow-up questions, general questions it should *answer* rather than run, and dangerous requests.
- **Graded by regex** (accepted and rejected forms, e.g. `apt` is wrong on Fedora). Each task also states the **expected safety tier**, so the report flags correct commands that would auto-run when they shouldn't, or prompt when they needn't.
- **Dangerous requests pass** only if the model refuses, or the command is blocked or needs `yes` typed in full. The run fails if any would have auto-run.
- **Metrics per model**: accuracy (mean ± SD across repeats), routing accuracy, consistency across repeats, p50/p95 latency, time to first token, generation tok/s, load time, VRAM, and per-category accuracy, with a table of every failure.
- Writes `results.jsonl` (every reply), `summary.md` and `meta.json` to `eval/results/<timestamp>/`.
- **The dataset is tested too**: every task has a reference answer that must pass its own grader at the expected tier. CI replays them (`--backend oracle`), and a fake Ollama server tests the streaming client, so the harness is checked without a GPU.

## Limitations

- **It's a 4B model.** It's good at single commands and short explanations, and unreliable at multi-step reasoning, obscure facts and anything agentic. It sits well below frontier cloud models.
- **The safety checks are a heuristic, not a sandbox.** The allowlist and patterns catch the common cases, but a determined or confused model could produce something they don't anticipate. Commands run as your user, which is why anything outside the read-only list needs your confirmation.
- **Learned rules go into the prompt**, so a long list eats into the 4K context window. It's capped at 40.
- **Fedora-specific.** The system prompt assumes Fedora with RPM Fusion. Other distros would need the prompts and package rules rewritten. The benchmark in `bench/` was run on the earlier Bazzite setup and still uses that prompt.
- **The original benchmark was small:** 9 tasks, one run each, graded by me. The eval harness above replaces it. Its regexes still can't recognise every valid way to write a command, so a failure in the report is worth reading before trusting.

## Install

Requires an NVIDIA GPU with the RPM Fusion driver (`akmod-nvidia` + `xorg-x11-drv-nvidia-cuda`) and Python 3.

```bash
# 1. Install Ollama as a system service (binds to localhost only by default)
curl -fsSL https://ollama.com/install.sh | sh
ollama pull qwen3.5:4b

# 2. Install the assistant
git clone https://github.com/Laith-18/local-ai-shell.git ~/projects/local-ai-shell
mkdir -p ~/.local/bin
ln -sf ~/projects/local-ai-shell/ai-shell.py ~/.local/bin/ai
ai
```

Inside `ai`: `/help`, `/learned`, `/unlearn <n>`, `/forget`, `/raw`, `/stats`, `clear`, `exit`.
Use a different model with `ai --model <name>` or `AI_SHELL_MODEL`.

To run the original speed benchmark: `bash bench/ai-bench.sh`. For accuracy, use the [eval harness](#eval-harness).
